# Capturing Content

A `Content` node stores or references material such as a transcription, an image, or an encoded document. Collections organise this material; annotations add structure, interpretation, or commentary.

For example, a transcription can belong to a witness through `PART_OF`. An annotation attached through `HAS_ANNOTATION` can mark a name or comment on a passage.

## Choosing Content Properties

Projects can refine `Content` into types such as `Text` or `Image`. They define the properties that store or reference the material. These names and properties are project choices; RAMEN does not prescribe them.

| Example type | Example property | What it holds                    |
| ------------ | ---------------- | -------------------------------- |
| `Text`       | `text`           | The transcription as plain text. |
| `Image`      | `url`            | A link to an image.              |

:::note[Tool requirements]

Agree on these properties with the tools that will capture and display the content. A tool needs to know which property contains the text or image reference.

:::

## Annotating Text and Images

`HAS_ANNOTATION` attaches an annotation to an object. An optional **selector** identifies the passage or region it describes. Without a selector, the annotation describes the whole object.

The text and image examples first show **where** an annotation applies. Their property excerpts omit identifiers and the annotation's own `type`. Complete records still require a project-declared annotation type. A selector's `type` specifies how a passage or region is located; it does not classify the annotation.

### Capturing Plain Text

A `TextPositionSelector` identifies a text range by its `start` and `end` positions. Counting starts at zero; the end position is excluded. In “plain text”, positions `0` to `5` select “plain”.

<Figure
  id="fig:capturing-text"
  number="2"
  src="/images/concepts/example-capturing-text.svg"
  alt="Text contains plain text. An annotation uses a TextPositionSelector with start 0 and end 5 to select plain. The annotation type is omitted from this excerpt."
  caption="A selector locates the annotated passage in the text."
  width={700}
/>

:::note[Text positions across tools]

The [W3C text-position convention](https://www.w3.org/TR/annotation-model/#text-position-selector) counts Unicode codepoints, not UTF-16 code units or displayed graphemes. It uses extracted text with markup removed and character entities resolved; selections should respect grapheme boundaries.

For exchange, tools also need to agree on the exact text, Unicode normalisation, and treatment of whitespace and line endings. Core stores the selector but does not enforce these conventions or normalise the content. The ASCII examples here give the same offsets under these different counting methods.

:::

Several annotations can describe the same or overlapping passages. Paragraphs, quotations, corrections, and different interpretations can therefore refer to the same text.

### Capturing Images

An image annotation can identify a region with a `FragmentSelector`. The value `xywh=50,40,120,90` describes a rectangle: `x` and `y` locate its top-left corner, and `w` and `h` give its width and height, in pixels.

<Figure
  id="fig:capturing-image"
  number="3"
  src="/images/concepts/example-capturing-image.svg"
  alt="An Image has an annotation whose selector uses FragmentSelector with value xywh=50,40,120,90. The rectangle starts at 50,40 and is 120 pixels wide and 90 pixels high."
  caption="A fragment selector describes a rectangular image region."
  width={700}
/>

For this fragment syntax, W3C recommends `conformsTo: "http://www.w3.org/TR/media-frags/"` in the selector object. It identifies the [Media Fragments specification](https://www.w3.org/TR/annotation-model/#fragment-selector). Core preserves this field but does not require or interpret it. The illustration includes this syntax identifier.

RAMEN follows the selector idea from the [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/#selectors). The tool interprets and checks the selector details, including whether a selection fits the content. See the [Core selector guide](https://ramen-suite.github.io/ramen-core/guides/ramen/selectors.html) for the stored format and validation limits.

## Typing Content Annotations

An annotation's `type` describes the kind of editorial annotation. A project can use a name such as TEI's [`persName`](https://tei-c.org/release/doc/tei-p5-doc/en/html/ref-persName.html) for a name occurrence. This remains an `Annotation` node; it does not require a separate node type for each kind of annotation.

<Figure
  id="fig:typed-annotation"
  number="4"
  src="/images/concepts/example-typed-annotation.svg"
  alt="The shared Annotation node has type persName. Its nested selector has type TextPositionSelector and selects Gaius at positions 0 to 5."
  caption="persName is the annotation type; TextPositionSelector is the selector type. They serve different purposes."
  width={700}
/>

In the current Core format, the annotation's `type` selects a project-declared **annotation shape**. The shape defines additional properties and permitted connections for that kind of annotation. It is separate from the node's modelled type and the selector's type.

## Linking Content Annotations

An annotation can also refer to another editorial object. For example, a `persName` annotation marks the name in “Gaius has …” and uses `REFERS_TO` to identify the person, `Gaius van B.`. A project can require that reference through the annotation shape.

<Figure
  id="fig:refers-entity"
  number="5"
  src="/images/concepts/example-content-refers-entity.svg"
  alt="A persName annotation selects Gaius in Gaius has … and REFERS_TO a Person entity labelled Gaius van B."
  caption="The text contains the written name; the annotation marks its occurrence; the entity represents the person."
  width={700}
/>

The same `Person` can be linked to mentions in other texts. The project can also use the shared `Annotation` node type for commentary or other shapes with different rules. Refining it into a separate node type is optional.

See the [reference model](/specification/reference-model#annotation-shapes-and-selectors) for shapes and selectors, and [Modelling Knowledge](/concepts/knowledge) for statements about entities.

## Editing Annotated Content

Changing a transcription can move or remove the passage an annotation selects. For example, inserting text before “Gaius” makes the old `0–5` selector point somewhere else. The [W3C model](https://www.w3.org/TR/annotation-model/#text-position-selector) also identifies this limitation of position selectors.

Tools need to retain the text revision used by each annotation. They can keep immutable content records or use a separate revision store. When text is edited in place, selectors need to be recalculated and checked; ambiguous matches need editorial review. A project can record the selected quote and its context to help locate a passage again.

RAMEN's reference model and Core do not provide a data revision store or automatic selector migration. A valid selector object alone does not establish that it still points to the intended passage.

## Reusing Existing Content

The following approaches are modelling options. Projects choose what to keep in an existing format and what to represent as separate RAMEN objects.

### Using TEI/XML and RAMEN

A project can reference an existing [TEI/XML](https://www.tei-c.org/) document and keep its encoding. Alternatively, it can extract text and map selected markup to annotations. The following example maps an `rs` element with `type="person"` and a `ref="#hevelius"` reference to an annotation of type `person` and a person entity. This preserves the type from the TEI example; it is a different project choice from `persName` above. The fragment reference points to a person entry with `xml:id="hevelius"` elsewhere in the TEI document; that entry is not shown here.

<Figure
  id="fig:tei-convert"
  number="6"
  src="/images/concepts/example-tei-content.svg"
  alt="TEI input uses rs with type person and ref #hevelius. It maps to plain text, an annotation of type person selecting positions 9 to 17, and a Person labelled Hevelius."
  caption="One possible mapping from TEI/XML to RAMEN. The selector positions refer to the extracted text."
  width={700}
  minWidth={600}
/>

Keeping text and annotation separate follows the general principle of standoff markup ([cf. Palladino et al. 2020](https://ceur-ws.org/Vol-3110/paper8.pdf)). TEI element names or attribute values can provide a vocabulary for annotations; each project still defines its shapes and mapping rules. The example shows selected markup, rather than a complete TEI conversion.

### Graph-Serialised Text with ATAG

Some projects need to address individual characters or tokens. _Applied Text as Graph_ (ATAG) represents these as linked nodes ([cf. Kuczera 2025](https://doi.org/10.4000/14vyl)).

<Figure
  id="fig:atag"
  number="7"
  src="/images/concepts/example-atag.svg"
  alt="A Text content node leads to the ATAG character chain t, e, x, t. An annotation points to the first and last characters through STANDOFF_START and STANDOFF_END."
  caption="An ATAG character chain connected to RAMEN content and annotation."
  width={700}
  minWidth={600}
/>

The RAMEN `Content` node provides access to the text. ATAG describes its internal structure. In this pattern, the character nodes and `STANDOFF_START` and `STANDOFF_END` links are managed by the tool and excluded from the instance graph passed to RAMEN Core. Core validates the RAMEN objects and their declared relationships; the tool checks the ATAG chain and its anchors separately.
