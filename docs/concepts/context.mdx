# Contextual Structures

A transcription can be read as the text of a particular copy of a letter, as part of a correspondence, or within a larger corpus. RAMEN uses **collections** to describe these contexts and how they fit together.

A `Content` node stores or references the material. A `Collection` groups content or other collections. The same content can belong to more than one collection.

## Collections and Membership

A project can refine `Collection` into types such as `Letter`, `Witness`, or `Corpus`. A witness is a surviving copy of a text. In a correspondence edition, a letter might bring together several witnesses, each with its own transcription and images.

`PART_OF` records membership. The project model defines which types can be connected and how many connections are allowed. For example, it can require each witness to belong to exactly one letter.

Collections can also have annotations. A project might attach commentary to a letter or annotate how a corpus was assembled. Other annotations can refer to a collection through `REFERS_TO`.

:::note[Ordering]

`PART_OF` records membership, not sequence. A project can attach an ordering annotation to a collection, refer to its members, and store their IDs in a declared `sequence` property, for example `["witness-record-a1", "witness-record-b1"]`. Alternatively, one annotation per member can refer to that member and store a declared numeric `position`, such as `1` or `2`. The order then belongs to that collection; the same object can have a different position elsewhere.

Tools must interpret these values and check membership, duplicate positions, and missing entries as required by the project. RAMEN assigns no built-in ordering meaning to `sequence`, `position`, or a property called `sort`.

A tool can instead maintain a `NEXT` chain internally. `NEXT` is not a RAMEN reference-model relationship. Such tool-specific links stay outside the instance graph passed to Core, and the tool checks the chain for cycles, branches, or missing members. For exchange as RAMEN data, use a declared ordering annotation.

:::

## Examples

These examples show possible project models. They describe **types and permitted relationships**, rather than individual records. Projects choose their structures to suit their material and research questions.

### Correspondence

A correspondence model can connect `Text`, `Witness`, `Letter`, and `Corpus` through `PART_OF`. The transcription belongs to a witness; the witness belongs to a letter; the letter belongs to a corpus.

One corpus can also belong to another. A project could group the correspondence between two people within its larger corpus of letters.

### Regesta

A regest summarises a document. In this example, the project type `Regest` groups each entry, with separate content for its title, summary, commentary, and archival history. The entry can belong to a volume, which belongs to a larger series or department.

This lets the project edit these texts separately while keeping them together as one entry.

### Books of Fortune

Books of fortune guide readers through questions, choices, and possible answers instead of a single sequence of pages ([cf. Cugliana et al. 2024](https://doi.org/10.17175/2024_005)).

A project can organise sections by their witness and version, while also grouping them into possible reading paths. In this example, `Concept` names the broader work structure and `GamePath` groups sections along one reading path. Both are project-specific collection types.

The example groups sections into a reading path without assigning that path to a version or concept. If a project needs that restriction, it can declare an additional `GamePath PART_OF Version` or `GamePath PART_OF Concept` relationship. The choice depends on whether paths stay within one version or cross versions.
